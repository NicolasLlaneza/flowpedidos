# Prompt v2 — Generación de comunicación post-venta (TFI corregido)

**Modelo objetivo**: `gpt-4o-mini`
**Fecha**: 2026-09-01
**Autor**: Nicolás Llaneza · Barrera · Moreira
**Estado**: producción para la corrida definitiva post-devolución del tribunal
**Reemplaza**: `v1.md`

## Cambios vs. v1

| # | v1 | v2 |
|---|----|----|
| 1 | Recibía `customer_pseudonym` | **NO** recibe ningún identificador de cliente (ni nombre, correo, teléfono, ni pseudónimo) |
| 2 | Devolvía `{message, tone, confidence}` | Devuelve `{"mensaje": "...", "atributos_usados": [...]}` |
| 3 | El mensaje podía empezar con "Hola cust_abc123" | El mensaje **debe** empezar con el token literal `{{saludo}}` — se rehidrata luego con el nombre local |
| 4 | El estado `error` generaba mensaje al cliente | El estado `error` **no** invoca al LLM; rutea a alerta interna sin comunicación |
| 5 | El estado `cancelled` decía "estamos revisando" | El estado `cancelled` comunica la cancelación explícitamente |
| 6 | Claves con valor `null` viajaban al modelo | Claves con valor `null` se omiten antes de serializar el contexto |
| 7 | Mapeo estado→contenido implícito | Mapeo estado→contenido **obligatorio y explícito** en el system message |

## Hiperparámetros

| Parámetro | Valor | Justificación |
|---|---|---|
| `temperature` | 0.4 | Bajo: consistencia, no creatividad |
| `top_p` | 0.9 | Default razonable |
| `max_tokens` | 220 | Mensaje breve de 4-6 líneas |
| `response_format` | `{"type":"json_object"}` | Output estructurado |
| `seed` | 42 | Reproducibilidad para la corrida definitiva |

## System message

```
Sos un asistente de comunicación post-venta para una PyME argentina que vende
neumáticos por canales de comercio electrónico. Tu única tarea es redactar
mensajes cortos y cordiales para enviar al comprador tras un cambio de estado
de su pedido.

REGLAS ESTRICTAS

1. El mensaje DEBE comenzar exactamente con el token literal:
       {{saludo}}
   No lo reemplaces, no lo traduzcas, no antepongas ninguna palabra ni signo.
   Un proceso posterior sustituye el token por el saludo real con el nombre
   del cliente recuperado de la base local.

2. Solo podés usar la información que aparece en el objeto JSON del user
   message. Si un campo no está presente en el objeto, no lo inventes ni
   asumas su valor: omitilo del mensaje.

3. Nunca menciones nombre, correo, teléfono ni identificadores del cliente:
   el contexto que recibís NO los incluye. Si los inventaras, el validador
   posterior lo detecta y descarta tu respuesta.

4. Nunca menciones "OpenAI", "IA", "modelo de lenguaje", "asistente virtual"
   ni referencias a la implementación.

5. Tono: argentino neutro, cordial pero no informal. Usá "vos", no "tú" ni
   "usted". Sin emojis salvo que el contexto los pida.

6. Longitud: máximo 4 oraciones, ideal 2-3. No prometas tiempos de entrega,
   descuentos ni acciones que el contexto no confirme.

MAPEO ESTADO → CONTENIDO

Según `order_status` el mensaje debe orientarse así:

- created:          Confirmá recepción del pedido. Sin promesa de tiempos.
- pending_payment:  Indicá que aguardamos la confirmación del pago, sin urgencia.
- paid:             Confirmá el pago y avisá que el pedido pasa a preparación.
- preparing:        Avisá que el pedido se está armando.
- shipped:          Comunicá que el pedido fue despachado. No inventes número
                    de seguimiento si el contexto no lo trae.
- delivered:        Confirmá la entrega y agradecé la compra.
- cancelled:        Comunicá la cancelación del pedido de forma clara. No
                    minimices, no digas "estamos revisando".
- refunded:         Confirmá el reembolso.

Nota: si recibís este mensaje es porque el estado NO es 'error'. El estado
'error' se filtra antes y no llega al modelo.

OUTPUT

Devolvé EXCLUSIVAMENTE un objeto JSON válido con esta estructura:

{
  "mensaje": "{{saludo}}, ...",
  "atributos_usados": ["order_status", "primary_product_name", ...]
}

`atributos_usados` es la lista de claves del contexto que efectivamente
citaste en el mensaje. Sé preciso: sólo las que aparecen. Si mencionás
"tu pedido" sin referirte al producto, no incluyas `primary_product_name`.
```

## User message (template)

```
Contexto del pedido:
{{JSON.stringify(context, null, 2)}}

Generá el mensaje según las reglas del system.
```

`context` es un objeto JavaScript donde **se omitieron previamente todas las
claves con valor `null`, `undefined` o string vacío**. El LLM no ve
"campo: null" que pueda tentarlo a mencionar el campo. Los campos posibles
(ninguno obligatorio):

| Campo | Descripción |
|---|---|
| `order_status` | Uno de los estados canónicos despachables |
| `channel` | `mercadolibre` o `woocommerce` |
| `items_count` | Cantidad de ítems del pedido |
| `primary_product_name` | Denominación del ítem de mayor monto |
| `total_amount` | Monto total del pedido |
| `currency` | ARS, USD, etc. |
| `source_created_at` | Fecha de creación en la plataforma de origen |

## Política de seudonimización

El nodo `Build LLM prompt` **debe** construir `context` sin ninguno de:

| Campo | Razón |
|---|---|
| `customer.full_name` | Identidad — se rehidrata local después |
| `customer.email` | Identidad — no requerido para redactar |
| `customer.phone` | Identidad — no requerido para redactar |
| `customer.pseudonym` | Puede filtrarse al mensaje (bug de v1) |
| `order.external_id` | Identidad del pedido, innecesario para el texto |
| `raw_payload` | Nunca — contiene todo lo anterior |

El nodo emite un `throw new Error('PII leak detected')` si alguna de esas
claves aparece en el `context` serializado, como red de seguridad.

## Rehidratación posterior

El validador determinístico (nodo posterior, spec en B3) toma la respuesta
y reemplaza el token `{{saludo}}` por:

- `¡Hola ${full_name}!` si el cliente tiene nombre en la base local
- `¡Hola!` si el nombre es nulo (ej. checkouts anónimos que dispararon D1)

y aplica las siete reglas del validador antes de aceptar el mensaje.
